# NotVisuals — Development roadmap

This is the **priority order** for the project. Stability fixes and tests accompany all phases; optimization and ports must not displace visual development.

## Phase 1 — Maximum visual quality

- **V0 — Visual baseline:** keep v7 as immutable visual reference; establish repeatable scenes in all dimensions and representative weather/lighting conditions.
- **V1 — Colour and exposure:** refine dynamic range, highlights, shadows, contrast, saturation, colour grading and brightness transitions.
- **V2 — Perceived lighting:** refine bloom extraction and scattering, glare, warm/cool tones and emission response where screen-space data allows it.
- **V3 — Atmosphere:** refine sky, fog, weather, clouds, sunrises, sunsets and night ambience using technically available render data.
- **V4 — World appearance:** tune water, vegetation, biomes, particles, Nether and End without promising access to unavailable physical-lighting inputs.
- **V5 — Image fidelity:** sharpen carefully, preserve pixel-art detail, avoid halos/ghosting/flicker, and prevent unwanted HUD treatment when possible.
- **V6 — Visual Gold Master:** resolve artifacts and regressions, standardise settings, record approved comparison captures and freeze the visual target.

**Exit criteria:** visual changes validated in-game across a documented scene matrix; no major visual defects; approved target appearance. Screen-space limits are documented honestly.

## Phase 2 — Optimisation without visual regression

- **O1:** profile GPU frame time, frame pacing and VRAM on representative hardware.
- **O2:** shorten render target lifetimes, reuse buffers when safe, minimise unnecessary full-resolution targets.
- **O3:** merge or downsample passes only when they match the Gold Master perceptually.
- **O4:** simplify shader math, samples and branching; check precision and driver behaviour.
- **O5:** benchmark before/after and keep the quality-maximal setting as the reference.

**Exit criteria:** measurable improvement with no unacceptable quality loss, no buffer hazards and no gameplay-breaking regressions.

## Phase 3 — Compatibility (last)

- **C0:** freeze and document the reference build, renderer dependencies and pack formats.
- **C1:** research version-specific post-processing APIs and shader interfaces.
- **C2:** create separate ports only when technical capabilities support a faithful appearance.
- **C3:** test every supported Minecraft version and publish clearly labelled variants.

**Exit criteria:** accurate version claims backed by real Minecraft testing and an explicit list of limitations.

## Release policy

- `main`: working, version-controlled **v7** baseline until a tested replacement is ready.
- Visual experiments: use branches or pull requests. Do not silently replace a published stable pack.
- Release assets: ZIPs generated by `scripts/build_pack.py`, never committed to Git.
- Source: the resource pack resides directly at the repository root.
